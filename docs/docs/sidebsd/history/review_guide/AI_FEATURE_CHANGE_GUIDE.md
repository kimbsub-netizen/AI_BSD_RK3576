# AI_FEATURE_CHANGE_GUIDE.md

## 목적

이 문서는 AI가 기존 Side BSD 프로젝트에 **기능 추가, 기능 개선, 동작 변경, 최적화**를 요청받았을 때 사용하는 상위 설계 지침이다.

목표는 사용자가 전문적인 설계 질문을 미리 만들 필요 없이 다음 정도의 요청만 해도 AI가 스스로 판단하도록 하는 것이다.

> "후진 기능을 개선해줘."
>
> "거리 관련 기능을 개선해줘."
>
> "이 기능을 추가해줘."

AI는 사용자의 요구를 문자 그대로 코드에 삽입하지 않는다.

먼저:

`요구사항 이해 → 기존 시스템 분석 → 기능 타당성 검토 → 유지/추가/조건부 적용/제거 판단 → 설계 → 영향 분석 → 구현 → 검증`

순서로 처리한다.

# 1. 기준 문서와 역할

기능 변경 전에 다음 자료를 기준으로 확인한다.

1. `docs/sidebsd/Side_BSD_시스템_기술_설계서.md`
   - 상세 설계와 현재 설계 의도 확인

2. `docs/sidebsd/Side_BSD_CODEBASE_OVERVIEW.md`
   - Side BSD 프로젝트 구조와 파일 위치 파악

3. `docs/sidebsd/review_guide/AI_PROJECT_CONTEXT.md`
   - 시스템 핵심 규칙과 불변 조건 확인

4. `docs/sidebsd/review_guide/AI_REVIEW_GUIDE.md`
   - 알고리즘/안전/데이터/실차 관점의 검증 방법 적용

5. 실제 현재 소스 코드
   - 실제 동작의 최종 구현 확인

문서와 코드가 다르면 임의로 하나를 선택하지 않는다.
차이점을 확인하고 현재 소스, 설계서, 변경 이력 등을 근거로 판단한다.

---

# 2. 기능 추가 요청의 기본 철학

새 기능을 요청받았을 때 "어떻게 추가할까?"부터 생각하지 않는다.

먼저:

> **이 기능이 정말 필요한가?**

를 판단한다.

그리고 기존 기능과의 관계를 확인한다.

가능한 결과는 다음 네 가지다.

1. **유지**
   - 기존 기능이 해당 모드에서도 필요함

2. **추가**
   - 기존 기능으로는 요구사항을 만족할 수 없음

3. **조건부 적용 / 모드별 분리**
   - 주행과 후진 등 운용 목적이 달라 특정 모드에서만 필요함

4. **제거 / 우회**
   - 기존 기능이 새로운 운용 목적과 충돌하거나 불필요함

필요하면 2~4를 조합한다.

---

# 3. 요구사항을 기능 단위로 재해석

사용자의 요청을 그대로 구현 요구사항으로 취급하지 않는다.

예:

> "후진 시 모든 장애물을 경고해줘."

를 받으면 다음처럼 재해석한다.

- 어떤 카메라가 후진에 참여하는가?
- 어떤 객체를 감지해야 하는가?
- 정지 객체도 반드시 감지해야 하는가?
- 기존 속도 필터가 필요한가?
- 기존 차량 필터가 후진에서도 의미가 있는가?
- ROI는 그대로 사용해야 하는가?
- 거리 기준이 주행용과 같아야 하는가?
- 방향지시등 조건은 후진에서도 의미가 있는가?
- 부저 조건은 후진 목적에 맞는가?
- Tracking이 필요한가?
- Scheduler 정책이 후진에서도 적합한가?
- 추론 빈도는 충분한가?
- 기존 주행 기능을 후진에서도 재사용해야 하는가?

이 질문들을 AI가 스스로 생성하고 검토한다.

---

# 4. 운용 모드가 달라지는 경우 우선 검토

다음과 같은 상태 변화가 있으면 단순 기능 추가가 아니라 **운용 모드 변경**으로 취급한다.

예:
- 주행 ↔ 후진
- 주간 ↔ 야간
- 실시간 ↔ 녹화 재생
- TEST ↔ PRODUCTION

운용 목적이 달라지면 기존 로직을 무조건 공유하지 않는다.

먼저 각 기능의 목적을 다시 평가한다.

차량용 Side BSD ↔ Forklift BSD 전환은 같은 애플리케이션의 운용 모드가 아니라
별도 제품/애플리케이션 경계로 취급한다. 공용 모듈을 재사용하더라도 요구사항,
설정, 경보 정책과 검증 문서를 서로 섞지 않는다.

---

# 5. 기능별 타당성 판단

기존 알고리즘/기능 각각에 대해 아래를 판단한다.

| 판정 | 의미 |
|---|---|
| KEEP | 그대로 유지 |
| MODIFY | 목적에 맞게 수정 |
| CONDITIONAL | 특정 모드에서만 적용 |
| BYPASS | 해당 모드에서 우회 |
| REMOVE | 더 이상 필요하지 않음 |
| ADD | 새로운 기능 필요 |
| REPLACE | 기존 방법을 다른 방법으로 교체 |

각 판단에는 반드시 이유를 붙인다.

예:

`VelocityTracker → REVERSE에서는 BYPASS 권고`

라고 판단했다면:

`왜 필요한지 → 왜 후진에서는 필요성이 낮아지는지 → 제거했을 때 장점 → 제거했을 때 위험 → 대안`

까지 설명한다.

---

# 6. 기존 기능의 목적을 먼저 파악한다

기존 기능은 "코드에 있으니까" 유지하는 것이 아니다.

예를 들어 속도 추정이 존재한다면:

- 경보 판정을 위해 필요한가?
- 오탐 제거를 위해 필요한가?
- tracking 품질을 위해 필요한가?
- 로그/진단만을 위해 필요한가?
- 다른 모듈에서 사용하는가?

를 확인한다.

기능의 원래 목적을 모르면 제거하지 않는다.

---

# 7. Side Camera와 Rear Camera를 자동으로 동일 취급하지 않는다

Side와 Rear는 시스템 목적이 다를 수 있다.

현재 설계에서도:

- Side Camera는 상대속도와 오작동 필터를 사용
- Rear Camera는 속도 필터를 사용하지 않고 거리 기반으로 장애물을 감지

하도록 구분되어 있다.

따라서 새로운 후진 기능을 추가할 때:

> "Rear처럼 Side도 동일하게 바꾸면 된다."

라고 자동 결론을 내리지 않는다.

Side Camera가 후진 시 어떤 역할을 수행하는지 실제 호출 흐름과 현재 필터를 확인한 뒤 결정한다.

---

# 8. 모드별 정책 분리 검토

주행과 후진처럼 목적이 크게 다른 경우 다음과 같이 명시적인 모드 정책을 우선 고려한다.

```text
FORWARD / DRIVING
    ├─ 주행용 객체 정책
    ├─ 주행용 속도 필터
    ├─ 방향지시등 연동
    └─ 주행용 경보 정책

REVERSE
    ├─ 후진용 객체 정책
    ├─ 장애물 누락 최소화
    ├─ 후진용 거리 기준
    ├─ 후진기어 연동
    └─ 후진용 경보 정책
```

단순한 `if reverse_gear_on:` 추가로 끝낼 수 있는지,
별도 정책 함수/모듈로 분리하는 편이 더 안전한지를 판단한다.

---

# 9. 안전 우선 판단

새 기능은 기능 추가 자체보다 **새로운 오탐/미탐을 만드는지** 먼저 검토한다.

## False Negative

새 변경으로 위험 객체를 놓칠 수 있는가?

특히:
- 필터가 객체를 제거하는가?
- 속도 미확정 때문에 억제되는가?
- ROI 밖으로 판단되는가?
- 거리 계산 실패 시 사라지는가?
- 오래된 결과가 사용되는가?
- 추론 주기가 너무 느려지는가?
- 모드 전환 순간에 결과가 유실되는가?

## False Positive

불필요한 경고가 늘어나는가?

특히:
- 반대편 차량
- 멀어지는 객체
- 정차 물체
- 그림자/영상 노이즈
- 잘못된 거리 보정

을 확인한다.

---

# 10. "모든 객체 감지"와 "모든 객체 경고"를 구분한다

사용자가:

> "모든 장애물을 경고"

라고 요청한 경우에도 다음 두 가지를 구분한다.

### Detection

모든 객체를 감지하는가?

### Decision

감지된 모든 객체를 실제 위험 객체로 판정하는가?

클래스 제한을 해제하는 것만으로 모든 장애물 경고가 완성되는 것은 아니다.

이후 단계의:

- ROI
- 거리
- 속도 필터
- 객체 필터
- 경보 조건
- 상태 조건
- 캐시

를 모두 확인한다.

---

# 11. 계산 자체가 필요한지 판단한다

새 모드에서 기존 연산이 실제 의사결정에 사용되지 않는다면,
다음 세 가지를 검토한다.

1. 그대로 계산
2. 해당 모드에서 계산을 건너뜀
3. 더 단순한 방식으로 대체

판단 기준:

- 경보 정확도
- NPU/CPU 사용량
- 지연시간
- 코드 복잡성
- 유지보수성
- 다른 기능의 의존성
- 로그/진단 필요성

단순히 "불필요해 보인다"는 이유만으로 제거하지 않는다.

---

# 12. 모드 전환을 별도로 검증한다

주행 → 후진 전환 시 상태가 이전 모드에서 남아있을 수 있다.

반드시 확인:

- tracker history
- velocity history
- alert state
- scheduler state
- cached detection
- rear session
- timer/counter
- stale result
- calibration state

필요한 경우 모드 전환 시:

- 유지
- 초기화
- 폐기
- 재초기화

중 어떤 것이 맞는지 판단한다.

---

# 13. 상태 오염(State Leakage) 검토

새 기능이 특정 모드에서만 동작한다면
다른 모드의 상태가 영향을 주지 않는지 확인한다.

예:

```text
DRIVING
  velocity history 생성
       ↓
REVERSE 진입
       ↓
기존 velocity history가 후진 판정에 사용됨
```

과 같은 상태 오염 가능성을 찾는다.

반대로 후진에서 생성한 상태가 주행 복귀 후 영향을 미치는지도 검토한다.

---

# 14. 성능 영향 검토

기능 추가 시 다음을 확인한다.

- CPU 증가
- NPU 증가
- inference FPS
- end-to-end latency
- frame queue
- worker 수
- memory
- task pile-up
- cache
- 스케줄러 fairness

기능을 추가해서 정확도가 올라가더라도
실시간성이 무너진다면 설계가 개선된 것으로 보지 않는다.

---

# 15. 중복 기능 검토

새 기능을 추가하기 전에 기존 시스템에 같은 기능이 있는지 확인한다.

확인:

- 동일 코드
- 유사 함수
- 동일 config
- 중복 상태
- 중복 계산
- 동일 목적의 다른 모듈

가능한 경우 기존 기능을 재사용하되,
목적이 다른 로직을 무리하게 통합하지 않는다.

---

# 16. 설정값 설계

새로운 동작이 configuration을 필요로 한다면:

- 기존 config에 추가할지
- mode별 config로 나눌지
- calibration 값인지
- logic threshold인지
- deployment switch인지

판단한다.

튜닝 가능한 값을 코드 상수로 박지 않는다.

또한:

`config 선언 → 실제 사용 → 호출부 → 영향`

전체 흐름을 확인한다.

---

# 17. 인터페이스 영향 분석

새 기능이 추가되면 다음 인터페이스를 확인한다.

- 함수 인자
- 반환값
- datatypes
- callback
- cache 구조
- scheduler
- HardwareIO
- OSD
- logging
- config
- test tool

기존 호출부를 모두 확인하지 않은 상태에서 함수 signature를 변경하지 않는다.

---

# 18. 테스트 요구사항도 함께 설계한다

기능 추가는 코드 수정으로 끝나지 않는다.

AI는 변경에 맞는 테스트 방법을 스스로 제안한다.

최소한 다음을 구분한다.

### Unit Test

수식/상태/조건 단위 검증

### Offline Video Test

녹화 영상 기반 동작 검증

### Calibration Test

거리/ROI/Optical Flow 관련 실측 검증

### Scenario Test

예:
- 정상 주행
- 후진 시작
- 정지 장애물
- 이동 장애물
- 보행자
- 자전거
- 차량
- 모드 전환
- 객체 소실/재등장

### Hardware Test

실제 CAN/GPIO/NPU/카메라 환경 검증

실제 데이터가 없으면 테스트 결과를 만들어내지 않는다.

---

# 19. 알고리즘 변경은 별도의 검증 수준 적용

다음 기능은 단순 기능 추가가 아니다.

- DistanceCalibrator
- VelocityTracker
- EgoSpeedEstimator
- EgoMotionFusion
- Scheduler
- 경보 판정

이런 기능을 변경할 경우 `docs/sidebsd/review_guide/AI_REVIEW_GUIDE.md`의 고수준 알고리즘 검증 절차를 적용한다.

즉:

`Concept → Math/Logic → Implementation → Data → Failure Mode → Production`

을 확인한 후 구현한다.

---

# 20. 기존 동작 회귀 검증

새 기능이 추가되었다고 기존 기능이 깨져도 되는 것은 아니다.

최소한:

```text
기존 모드 정상 동작
+
새 모드 정상 동작
+
모드 전환 정상 동작
```

세 가지를 확인한다.

예:

후진 기능을 추가했다면:

- 전진 주행 BSD가 기존과 동일하게 동작하는가?
- 후진에서 새로운 정책이 동작하는가?
- 후진 → 주행 복귀 시 기존 상태가 정상 복구되는가?

를 확인한다.

---

# 21. 구현 전 설계 판단 결과를 먼저 정리

복잡한 기능 변경이면 코드 수정 전에 아래를 먼저 정리한다.

## 요구사항

사용자가 원하는 결과

## 현재 동작

현재 코드가 실제로 하는 것

## 발견된 문제

현재 구조에서 요구사항과 충돌하는 부분

## 기능별 판단

| 기능 | 판단 | 이유 |
|---|---|---|
| 기능 A | KEEP | ... |
| 기능 B | CONDITIONAL | ... |
| 기능 C | BYPASS | ... |
| 기능 D | ADD | ... |

## 제안 구조

변경 후 데이터 흐름/모드 흐름

## 영향 범위

수정될 파일과 영향을 받을 파일

## 위험

회귀/성능/안전 위험

## 검증 방법

변경 후 무엇으로 확인할 것인지

사용자가 구현까지 요청한 경우 그 후 구현한다. 분석만 요청했거나 설계 선택이
결과를 크게 바꾸는 미확정 사항이 있으면 분석 결과를 제시하고 구현을 멈춘다.

단, 사용자가 "분석만" 요청한 경우에는 여기서 멈추고 코드를 수정하지 않는다.

---

# 22. "요구사항보다 더 좋은 설계"를 제안할 수 있다

사용자가 요구한 방법보다 더 나은 구조가 있다면 제안한다.

예:

사용자 요구:

> "후진일 때 속도 필터를 꺼줘."

AI 판단:

> "속도 필터 하나만 끄는 것보다 Reverse Policy를 별도로 두고,
> 관련된 차량 방향 필터/경보 조건/부저 조건을 함께 분리하는 것이
> 기능 목적과 유지보수 측면에서 더 적절하다."

이 경우 단순 요구사항을 그대로 구현하지 않고
더 안전한 구조를 제안할 수 있다.

단, 기존 구조를 크게 바꾸는 경우에는:

`현재 구조 → 제안 구조 → 장점 → 단점 → 회귀 위험`

을 먼저 설명한다.

---

# 23. 작은 변경과 큰 변경을 구분한다

## Small Change

예:
- 로그 추가
- 특정 config 연결
- 표시 문구 변경

→ 영향 범위를 확인하고 바로 구현 가능

## Medium Change

예:
- 새로운 필터
- 새로운 threshold
- 기존 함수의 동작 변경

→ 의존성/회귀/테스트를 검토한 후 구현

## Large Change

예:
- 새로운 운용 모드
- 핵심 알고리즘 변경
- Side/Rear 처리 정책 변경
- Scheduler 구조 변경

→ 반드시:

`요구사항 → 타당성 → 설계 → 영향 → 구현 → 검증`

순서로 진행한다.

---

# 24. 사용자의 요청이 모호해도 필요한 판단을 AI가 한다

사용자가:

> "후진할 때 사이드 카메라를 좀 개선해줘."

라고 요청해도 먼저 다음을 스스로 조사한다.

- 후진 시 현재 SideCamera 흐름
- 전체 객체 감지 여부
- 속도 추정 사용 여부
- 마주오는 차량 필터
- 멀어지는 객체 필터
- ROI
- 거리 계산
- 경보 거리
- 방향지시등
- 후진기어
- 부저/LED
- Tracking
- Scheduler
- cache
- mode transition

그리고 문제/개선점을 정리한다.

사용자에게 전문적인 질문을 되묻기 전에
현재 프로젝트 자료와 코드를 이용해 최대한 판단한다.

---

# 25. 최종 출력 원칙

기능 변경 작업의 최종 결과는 다음 순서를 권장한다.

## 1. 판단

무엇을 바꾸는 것이 맞는지

## 2. 근거

왜 그렇게 판단했는지

## 3. 변경 범위

어떤 파일/모듈이 영향을 받는지

## 4. 설계

어떤 구조로 바꿀 것인지

## 5. 구현

실제 코드 변경

## 6. 검증

무엇을 확인했는지

## 7. 추가 검증 필요사항

실측/실차가 필요한 부분

---

# 26. 중요한 금지사항

다음 행동은 하지 않는다.

- 사용자 요구를 무조건 그대로 코드로 옮김
- 요구사항과 관계없는 대규모 리팩터링
- 설계 검토 없이 핵심 알고리즘 변경
- 기존 안전장치 삭제
- TEST 기능을 PRODUCTION으로 확장
- 실제 데이터가 없는 상태에서 성능을 확정
- 코드 변경만으로 실제 차량 성능을 보장한다고 주장
- 기존 모드 회귀 검증 없이 새 모드만 테스트
- 관련 호출부와 config를 확인하지 않고 interface 변경
- 새로운 상태를 추가하면서 mode transition/state leakage를 확인하지 않음

---

# 27. 최종 의사결정 원칙

AI의 역할은 단순히 "사용자가 원하는 기능을 만들어주는 것"이 아니다.

AI는 다음을 판단해야 한다.

> 이 기능이 필요한가?

> 기존 기능 중 무엇을 유지해야 하는가?

> 무엇을 제거하거나 우회해야 하는가?

> 주행/후진처럼 모드가 다르면 정책을 분리해야 하는가?

> 더 단순하고 안전한 설계가 있는가?

> 기존 기능에 어떤 부작용이 생기는가?

> 실제 데이터가 있어야 결정할 수 있는 것은 무엇인가?

> 구현 후 무엇을 시험해야 하는가?

최종 목표는:

**요구사항 충족 + 기존 기능 보존 + 불필요한 기능 제거/우회 + 안전성 + 실시간성 + 검증 가능성**

을 동시에 만족하는 변경을 만드는 것이다.
